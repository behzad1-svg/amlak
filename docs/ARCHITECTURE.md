# معماری CRM ساج — املاک ساج (بوشهر)

> سند زندهٔ معماری سیستم. آخرین بازبینی: **۱ آذر ۱۴۰۵** — بر اساس کد مخزن (کامیت `48abbf9`) و وضعیت زندهٔ سرور.
> این سند **هیچ رازی ندارد**: پسورد، DSN، توکن و connection string اینجا نوشته نمی‌شود؛ فقط محل نگهداری‌شان ذکر شده است.

## ۱. سیستم چیست

CRM تک‌مستأجره (single-tenant) برای یک بنگاه املاک در بوشهر: ثبت فایل (ملک) و مشتری، تطبیق خودکار مشتری↔فایل، بازدید، کارت جلسه، معامله و حسابداری (کمیسیون، شیرینی، صندوق). کاربران: **مدیر (OWNER)** و **مشاور (AGENT)** — حدود ۱۵ تا ۲۰ نفر.

- آدرس زنده: `https://crm.amlaksaj.ir`
- مخزن: `behzad1-svg/amlak` (عمومی)، شاخهٔ `main`
- زبان رابط کاربری: فارسی، راست‌به‌چپ، تاریخ جلالی (کتابخانهٔ `jalaali-js`)

## ۳. توپولوژی استقرار

```
اینترنت
   │  (HTTPS :443 — فقط از بازه‌های WCDN؛ :80 برای HTTP-01 تمدید گواهی)
   ▼
WCDN پار‌سپک (CDN + محافظ)
   │  (هدر X-Real-IP با IP واقعی کاربر)
   ▼
Caddy  (روی VPS، :443 و :80)
   │  reverse_proxy به 127.0.0.1:3000
   │  trusted_proxies = فقط بازه‌های رسمی WCDN (لیست ثابت در Caddyfile)
   ▼
Next.js — systemd service saj-crm  (Node 22، 127.0.0.1:3000)
   │
   ├──► PostgreSQL 16 (127.0.0.1:5432، دیتابیس saj_crm_db)
   │
   └──► (خارج از مسیر درخواست) cron ها: بکاپ شبانه، یادآوری ساعتی
```

**نکتهٔ مهم — زنجیرهٔ اعتماد IP:** اپ فقط هدر `X-Real-IP` را می‌خواند (`src/lib/clientIp.ts`) و فقط وقتی `TRUSTED_PROXY=true` باشد. Caddy فقط به بازه‌های WCDN اعتماد می‌کند و `X-Real-IP` را از IP واقعی می‌سازد؛ `X-Forwarded-For` **هرگز** خوانده نمی‌شود (اولین ورودی‌اش قابل جعل است). اتصال مستقیم به `:443` از بیرون با UFW بسته است و اتصال مستقیم به `:3000` فقط از خود سرور ممکن است.

## ۴. اجزای اپلیکیشن

### ۴.۱ ساختار کد (`src/`)

- **`src/app/`** — صفحات App Router: `(dashboard)/` (داشبورد، مشتریان، فایل‌ها، تطبیق، حسابداری، کارت جلسه، بازدیدها، دفترچه تلفن، گزارش‌ها، کاربران، تنظیمات) + `/login` (سرورکامپوننت + فرم جدا `LoginForm.tsx`).
- **`src/app/api/`** — حدود ۴۰ مسیر API: `auth/*`، `customers/*`، `properties/*`، `deals/*`، `accounting/*`، `session-cards/*`، `matching/*`، `viewings/*`، `phonebook/*`، `users/*`، `settings`، `notifications`، `activities`، `tasks`، `follow-ups/*`، `reports/*`، `admin/*`، `cron/reminders`، `health`، `seed` (قفل‌شده).
- **`src/proxy.ts`** — دروازهٔ اول احراز هویت (جایگزین `middleware.ts` در Next 16). فقط **امضای** JWT را چک می‌کند؛ بررسی لغو نشست (`tokenVersion`) و فعال‌بودن کاربر با دیتابیس، در layout داشبورد و مسیرهای API انجام می‌شود (موتور نیتیو Prisma در باندل پروکسی قابل استفاده نیست). مسیرهای عمومی: `/login`، `/api/health`، `/api/auth/login`، `/api/cron/reminders` (با `CRON_SECRET`)، `/api/admin/backup-log` (POST با `CRON_SECRET`)، فایل‌های PWA و لوگو.
- **`src/lib/`** — منطق دامنه: `auth.ts`، `jwt.ts`، `access.ts` (مجوز + ماسک)، `permissions.ts`، `matching.ts`، `shares.ts` (تقسیم کمیسیون)، `cashbox.ts`، `sessionCards.ts`، `backup.ts`، `clientIp.ts`، `rateLimitDb.ts`، `jalali.ts`، `money.ts`، `audit.ts`، `apiErrors.ts`، `dashboard.ts`، `phonebookMerge.ts`، `pricePerSqm.ts`، `propertyCode.ts`.
- **`src/components/`** — کامپوننت‌های UI (کارت، مودال، `JalaliDatePicker`، `MoneyInput` و…)؛ `SwRegister.tsx` ثبت Service Worker برای PWA.

### ۴.۲ احراز هویت و نشست

- **توکن:** JWT با الگوریتم HS256 (کتابخانهٔ `jose`)؛ payload فقط `userId`، `role`، `tokenVersion`. اعتبار **۲۴ ساعت**.
- **کوکی:** `saj_token` — `httpOnly`، `secure` (در production)، `sameSite=strict`، `path=/`.
- **پسورد:** bcrypt با cost ‏۱۰؛ حداقل **۱۲ کاراکتر، حروف لاتین + عدد** (سیاست ثبت کاربر).
- **لغو نشست:** هر خروج، تغییر پسورد یا غیرفعال‌شدن کاربر، `tokenVersion` را یکی زیاد می‌کند و همهٔ JWTهای قبلی بی‌اعتبار می‌شوند (`invalidateUserTokens`).
- **محدودیت نرخ ورود** (جدول `RateLimitHit` در دیتابیس، نه حافظه): هر شماره تلفن **۵ تلاش ناموفق در ۱۵ دقیقه**، هر IP ‏۲۰ تلاش؛ بعد از آن ورود قفل می‌شود تا پنجره بگذرد.
- **بازیابی پسورد ندارد** (تصمیم مدیر — تا اطلاع ثانوی ساخته نمی‌شود). راه بازیابی: مدیر دیگر از صفحهٔ `/users` پسورد را ریست می‌کند، یا ریست مستقیم از سرور (رجوع به Runbook).

### ۴.۳ نقش‌ها و مجوزهای دانه‌ای

| نقش | خلاصه |
|---|---|
| `OWNER` (مدیر) | همه‌چیز: مدیریت کاربران، تنظیمات، حذف، گزارش کامل حسابداری، ردیف «دفتر» |
| `AGENT` (مشاور) | مشتری‌ها و فایل‌های خودش + فایل‌های تیم (با ماسک، بخش ۴.۴)؛ حذف فقط اگر تیک مجوزش خورده باشد |

مجوزهای دانه‌ای هر مشاور (`src/lib/permissions.ts`، در ستون `permissions` جدول User به‌صورت JSON):

| کلید | برچسب | پیش‌فرض مشاور |
|---|---|---|
| `canCreateProperty` | ثبت فایل | روشن |
| `canArchiveProperty` | بایگانی فایل | روشن |
| `canDeleteProperty` | حذف فایل | **خاموش** |
| `canCreateCustomer` | ثبت مشتری | روشن |
| `canCreateDeal` | ثبت معامله | روشن |
| `canCreatePhonebook` | ثبت دفترچه تلفن | روشن |
| `canDeletePhonebook` | حذف دفترچه تلفن | **خاموش** |

مدیر همیشه همهٔ مجوزها را دارد. حذف (soft-delete) رکوردهای اصلی بدون نقش مدیر با ۴۰۳ رد می‌شود.

### ۴.۴ دسترسی به فایل و ماسک اطلاعات تیم

مدل دسترسی فایل سه لایه است (`src/lib/access.ts`):

1. **دسترسی کامل** (`canAccessPropertyFull`): مدیر، ثبت‌کنندهٔ فایل، فایل دفتر (`isOfficeFile`)، یا فایل `TEAM_VISIBLE`.
2. **دسترسی اعطاشده** (`PropertyAccess`): مدیر می‌تواند برای یک فایل مشخص به مشاور خاص تیک بزند. **تیک = مشاهدهٔ کامل + حق آگهی‌کردن همان فایل** (تصمیم ۱ آذر ۱۴۰۵)؛ برداشتن تیک هر دو را می‌گیرد. ردیف `PropertyAccess` برای هر `(propertyId, userId)` یکتاست؛ اعطای دوباره همان ردیف را به‌روز می‌کند.
3. **نمای تیم** (`maskPropertyForTeam`): مشاوری که فقط TEAM_VISIBLE می‌بیند، **قیمت و منطقه را می‌بیند** ولی **آدرس دقیق، نام/تلفن مالک و توضیحات فایل** برایش حذف می‌شود. قیمت باز است، مالک بسته است، آدرس دقیق هرگز برای مشاور دیگر دیده نمی‌شود (تصمیم مدیر، ۱ آذر ۱۴۰۵). توجه: اگر آدرس دقیق داخل **عنوان** فایل نوشته شده باشد، در نمای تیم دیده می‌شود.

خواندن فایل مشاور دیگر **by design** آزاد است (برای تطبیق لازم است)؛ نوشتن (کارشناسی `appraise` و آگهی `advertise`) روی فایل دیگری بدون دسترسی، ۴۰۳ می‌گیرد — این دو مسیر در ۱ آذر ۱۴۰۵ اصلاح و راستی‌آزمایی شدند.

### ۴.۵ دفترچه تلفن و یکپارچگی با مشتریان

دفترچه تلفن (`PhonebookContact`) یک فهرست واحد با مشتریان است: شمارهٔ مشتری زنده هرگز کپی نمی‌شود؛ مالک/فروشنده زیر «مالک» و خریدار/مستاجر زیر «خریدار» با نشان «مشتری» و لینک به پروفایل دیده می‌شوند. **دیده‌شدن فقط مالِ خودِ مشاور است** (مدیر همه را می‌بیند)؛ هر مشاور فقط شماره‌هایی را می‌بیند که خودش ثبت کرده است. هر شمارهٔ فعال در دفترچه یک رکورد دارد (یکتایی با partial unique index).

**قواعد یکتایی مهم:**
- شمارهٔ مشتری در هر دسته یک‌بار برای رکوردهای فعال (partial unique index — `prisma db push` نمی‌تواند partial index بسازد، پس در اسکیما نیست؛ فایل SQL جداست).
- `PropertyAccess` یکتا به‌ازای (فایل، کاربر)؛ `MatchDismissal` یکتا به‌ازای (مشتری، فایل).
- **صندوق:** فقط یک IN به‌ازای هر معامله و یک OUT به‌ازای هر سهم — با unique indexهای جزئی (`prisma/cashbox-unique-indexes.sql`).
- مبالغ پول **BigInt تومان**؛ درصدها Decimal با دقت صدم درصد؛ گرد کردن «نیم به بالا» (`shares.ts`).

## ۶. جریان‌های کلیدی کسب‌وکار

### ۶.۱ تطبیق مشتری ↔ فایل (`src/lib/matching.ts`)

- فیلترهای سخت: نوع معامله، نوع ملک، منطقه — اگر نخواند، تطبیق اصلاً حساب نمی‌شود.
- امتیاز وزنی: **بودجه ۰٫۶ / متراژ ۰٫۲۵ / خواب ۰٫۱۵**. آستانهٔ نمایش **۷۰**؛ اعلان فقط برای امتیاز **۸۰ به بالا** (۹۰ به بالا = HIGH).
- منحنی بودجه: اوج ۱۰۰ دقیقاً روی سقف؛ بازهٔ [۰٫۹۵ سقف، سقف] ۹۵ تا ۱۰۰؛ بالای سقف تا ۱۰٪ بالاتر ۹۰ تا ۷۰ نزولی؛ بالای ۱۱۰٪ سقف **رد** می‌شود. برای اجاره، ودیعه و اجارهٔ ماهانه جدا حساب می‌شوند و معادل ماهانهٔ ودیعه با تقسیم بر ۳۰ میلیون تومان برآورد می‌شود.
- فقط فایل‌های ACTIVE و مشتری‌های غیر LOST/FAILED/WON تطبیق می‌خورند؛ تطبیق «علاقه‌ای ندارد» پنهان می‌شود ولی پاک نمی‌شود.
- تطبیق **همگام در مسیر درخواست** اجرا می‌شود (صف واقعی هنوز ساخته نشده است)؛ اعلان‌ها گروه‌بندی می‌شوند (یک اعلان برای چند تطبیق) و در ۲۴ ساعت گذشته تکراری ساخته نمی‌شود.
- حذف نرم فایل/مشتری، اعلان‌های MATCH_SUGGESTION مربوطش را هم پاک می‌کند.

### ۶.۲ کارت جلسه (`SessionCard`)

مشاور کارت را پر می‌کند (مشتری + فایل/مالک، تاریخ+ساعت، وجه نقد، قصد، شیرینی مالک، دستمزد/کمیسیون، شرایط پرداخت، یادداشت). با ثبت، **اعلان فوری HIGH به همهٔ مدیران** + به هر همکار (حداکثر **۳ نفر**، در UI و سرور اجبار می‌شود) + مدیر قرارداد انتخاب‌شده می‌رسد. وضعیت: PENDING ←→ CONFIRMED/CANCELLED؛ CANCELLED نهایی است. ویرایش فقط تا وقتی PENDING است و فقط توسط سازنده. (نکتهٔ باز: تغییر همکارها در ویرایش، اعلان ندارد.)

### ۶.۳ معامله و حسابداری (`src/lib/shares.ts`)

- قیمت معامله **جدا از قیمت فایل** است؛ معاملهٔ تازه قیمت فایل را به‌عنوان نقطهٔ شروع کپی می‌کند و مدیر می‌تواند قیمت نهایی توافقی را در حسابداری عوض کند — کمیسیون از **قیمت نهایی** حساب می‌شود.
- انتساب معامله: `agentId` معامله = مشاورِ منتسب به مشتری، نه کسی که «موفق» را زده است.
- **مبنای تقسیم = کمیسیون + شیرینی فروشنده + شیرینی خریدار − تخفیف.** دفتر `officePct` (پیش‌فرض ۵۰٪) می‌گیرد؛ بقیه بین سهم‌ها تقسیم می‌شود؛ مجموع دفتر + سهم‌ها باید **دقیقاً ۱۰۰٪** شود (تلرانس ۰٫۰۱). «تعاون» سهم همکار بیرونی است (بدون userId، با نام متنی) و در جمع کل گزارش‌ها **حساب نمی‌شود** — در پانوشت جداست.
- **دفتر خودش یک طرف حساب است** (تصمیم ۳۰ آبان ۱۴۰۵): معامله‌ای که سهم واقعی ندارد، سهم مجازی ۱۰۰٪ به مشاور نمی‌گیرد؛ دفتر `officePct` ذخیره‌شده را می‌گیرد و بقیه سهم مجازی مشاور معامله می‌شود. همهٔ مسیرها باید از `resolveSplit` بگذرند؛ خواندن مستقیم `officePct` ممنوع است (وگرنه عددها با هم نمی‌خوانند).
- **مالیات فقط روی کمیسیون است** (پیش‌فرض ۱۰٪، از تنظیمات قابل تغییر)؛ شیرینی مالیات ندارد. تخفیف مبنای تقسیم و مبلغ پرداختی را کم می‌کند ولی **مبنای مالیات را نه**. نرخ مالیات در لحظهٔ ثبت کمیسیون مهر می‌شود.
- کمیسیون فروش با مبلغ×درصد چک می‌شود (تلرانس ۱۰۰ تومان برای گرد کردن)؛ لغو معامله‌ای که پولش گرفته شده یا سهمی تسویه شده باشد، بسته است؛ بعد از تسویهٔ هر سهم، تقسیم قفل می‌شود.
- **قانون صندوق:** فقط یک IN به‌ازای هر معامله و یک OUT به‌ازای هر سهم، تا ابد (unique index، بخش ۵). با دریافت/تسویهٔ دوباره بعد از برگشت، رکورد برگشت **حذف** می‌شود تا رکورد اصلی دوباره فعال شود؛ تاریخچهٔ کامل در `AuditLog` می‌ماند. سهم دفتر یک طلب است، نه پول نقد — تا وقتی «دریافت شد» نخورده، صندوق صفر می‌ماند.

### ۶.۴ انتقال مشتری

مشاور می‌تواند مشتری خودش را مستقیم به مشاور دیگر منتقل کند، بدون تأیید مدیر. ولی **مشتری منتقل‌شده دست‌به‌دست نمی‌شود**: گیرنده فقط می‌تواند او را به مشاور قبلی برگرداند؛ انتقال به هر مقصد دیگری فقط با مدیر است (۴۰۳ سمت سرور). انتقال در `CustomerTransfer` و اعلان `CUSTOMER_TRANSFERRED` ثبت می‌شود.

### ۶.۵ بلاک ثبت فایل تکراری

سرور ثبت فایل با **همان مالک + همان آدرس + همان متراژ + همان نوع + همان نوع معامله** را برای مشاور رد می‌کند (۴۰۹، با کد فایل موجود و نام ثبت‌کننده). مدیر معاف است. اگر آدرس وارد نشده باشد، ملاک منطقه است. همان مالک با آدرس/متراژ متفاوت = ملک دیگر و ثبتش آزاد است.

### ۶.۶ پیگیری و یادآوری

- پیگیری سررسیددار روی مشتری (`FollowUp`)؛ تاریخ‌های زمان‌بندی‌شده نمی‌توانند در گذشته باشند (انتخاب‌گر جلالی، `min = today`؛ استثنا `allowPast` برای ورودی‌های غیر زمان‌بندی).
- زمان‌ها naive ذخیره می‌شوند (`TIMESTAMP(3)` = دیوارهٔ UTC لحظه)؛ انتخاب‌گر تاریخ را روی **۱۲:۰۰ تهران** قفل می‌کند.
- کرون ساعتی (`/api/cron/reminders` با `CRON_SECRET`) اعلان می‌سازد: پیگیری‌های سررسیدگذشته/امروز → `FOLLOW_UP_OVERDUE` (گذشته = HIGH)؛ بازدیدهای ۲ ساعت آینده و فردا → `VIEWING_REMINDER`.
- مشتری راکد: بدون فعالیت بیش از سقف مرحله‌اش (تماس اولیه ۳ روز، مذاکره/بازدید/قرارداد ۷ روز).

### ۶.۷ گزارش عملکرد

مدیر همهٔ مشاوران + جمع کل را می‌بیند؛ مشاور فقط **ردیف خودش** را می‌بیند — API سمت سرور فقط همان ردیف را برمی‌گرداند و جمع کل برابر همان ردیف است، پس حتی با صدای مستقیم API هم عدد مشاور دیگر نشت نمی‌کند. ردیف «دفتر» فقط برای مدیر است (مشاور ۴۰۳ می‌گیرد).

## ۷. بکاپ، مانیتورینگ، مشاهده‌پذیری

- **بکاپ شبانه:** ساعت ۰۳:۰۰ تهران، `pg_dump -Fc` + gzip به `/opt/saj-crm/backups/` (چرخش ۷ روزه روی سرور) + کپی با rclone به Google Drive (پوشهٔ `saj-crm-backups`؛ در Drive چرخش ندارد — همهٔ بکاپ‌ها از ۲۵ آبان ۱۴۰۵ نگه داشته می‌شوند). **بدون رمزگذاری** (تصمیم مدیر). هر بکاپ (شبانه یا دستی) در جدول `BackupLog` و صفحهٔ مدیریت ثبت می‌شود.
- **بکاپ دستی:** مدیر از `/api/admin/backup` (فقط OWNER) خروجی `pg_dump` را مستقیم دانلود می‌کند؛ فقط یک بکاپ دستی هم‌زمان.
- **بازیابی آزموده‌شده:** restore کامل در دیتابیس تست (۲۶ آبان) و در Neon برای تمرین DR (۱ آذر) با موفقیت انجام شد. تست wipe-and-restore روی سرور زنده **تأیید نشده** و انجام نمی‌شود مگر مدیر بگوید.
- **سلامت:** `GET /api/health` → `{"status":"ok","dbMs":N}` (۲۰۰)؛ خطای دیتابیس → ۵۰۰. مانیتور آپتایم هر ۱۰ دقیقه همین را چک می‌کند.
- **Sentry:** خطاهای سرور و کلاینت به پروژهٔ `saj-crm` می‌روند. کلاینت مینیمال است: فقط وقتی `NEXT_PUBLIC_SENTRY_DSN` ست باشد، فقط production، `tracesSampleRate: 0`، بدون replay/feedback، بدون اطلاعات کاربر و بدون بدنهٔ HTTP (شمارهٔ مشتری در بدنه‌هاست). خطاهای سمت سرور در `/api/admin/error-logs` هم برای مدیر دیده می‌شوند (جدول `ApiErrorLog`).
- **لاگ‌ها:** `journalctl -u saj-crm` (اپ)، `/var/log/saj-backup.log` (بکاپ)، `/var/log/saj-cron.log` (یادآوری‌ها)، `AuditLog` در دیتابیس (تغییرات).

## ۹. تصمیم‌های کلیدی و دلیلشان

| تصمیم | دلیل |
|---|---|
| تک‌مستأجره، بدون Docker | یک دفتر، یک سرور؛ سادگی عملیات مهم‌تر از مقیاس‌پذیری بود. SaaS مرحلهٔ بعد است، بعد از جاافتادن محصول — نه حالا |
| `prisma db push` به‌جای migration | تیم کوچک، اسکیما در حال تکامل سریع؛ migration بعداً اگر لازم شد |
| JWT سفارشی به‌جای NextAuth | کنترل کامل روی نشست و لغو توکن (`tokenVersion`)؛ وابستگی کمتر |
| ماسک تیم به‌جای پنهان‌کردن کامل فایل‌ها | مشاورها برای تطبیق باید قیمت و منطقهٔ فایل همکار را ببینند؛ ولی آدرس دقیق و مالک محرمانه است |
| تطبیق همگام، بدون صف | حجم کم (تیم ~۱۵ نفر)؛ صف واقعی قدم بعدی است، نه پیش‌نیاز لانچ |
| دفتر طرف حساب در تقسیم | سهم و درآمد دفتر باید مشخص و قابل پیگیری باشد، نه عدد مجازی صفر |
| بکاپ بدون رمزگذاری | تصمیم مدیر؛ سرعت بازیابی و سادگی مهم‌تر بود |
| بدون import انبوه | مدیر گفت دستی وارد می‌کنند |

## ۱۰. شکاف‌های شناخته‌شده (از چک‌لیست لانچ، ۱ آذر ۱۴۰۵)

- تست هم‌زمان چند کاربر، تست قطعی شبکه و تست DR کامل روی سرور هنوز انجام نشده.
- تست خودکار فرانت‌اند فقط یک فایل؛ پوشش تست مسیرهای API ناقص؛ تست E2E ندارد.
- آموزش مشاوران و اطلاع‌رسانی رسمی لانچ انجام نشده.
- تمرین DR روی Netlify + Neon با **تمام‌شدن اعتبار رایگان Netlify** (۳۰۰ واحد در ماه، چرخه تا ۱۸ آذر) متوقف است؛ دیپلوی از ۱۹ آذر دوباره ممکن می‌شود، مگر ارتقا داده شود.
- اعلان تغییر همکارها در ویرایش کارت جلسه ساخته نمی‌شود (سؤال باز از مدیر).
- چیپ «موفق» برای مشتری‌های WON پنهان در کانبان ساخته نشده (سؤال باز از مدیر).
- سه فهرست توجه صفحهٔ قدیمی `/today` (لیدهای بی‌جواب، فایل‌های بدون بازدید در ۳۰ روز، بازدیدهای بدون گزارش) بعد از ادغام در داشبورد، دیگر در دسترس نیستند (سؤال باز از مدیر).
- سرخط صفحهٔ فایل حذف‌شده هنوز «داده بارگذاری نشد» می‌گوید (پولیش باز).
- مهلت وظیفه‌ها (`Task.dueAt`) فقط تاریخ نشان می‌دهد، بدون ساعت (سؤال باز از مدیر).

## ۱۱. چیزهایی که در این سند تأیید نشد

- رفتار دقیق Caddy موقع تمدید خودکار گواهی (LE) — فقط از روی پیکربندی و تاریخ انقضا (۲۴ بهمن ۱۴۰۵) می‌دانیم؛ تمدید واقعی هنوز رخ نداده است.
- ظرفیت واقعی هم‌زمان (concurrent users) — تست نشده.
- مسیر ریست مستقیم پسورد از سرور (وقتی هیچ مدیری نمی‌تواند وارد شود) اسکریپت آماده ندارد — در Runbook به‌عنوان شکاف ثبت شده است.
